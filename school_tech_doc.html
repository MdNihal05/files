§ 1

Overview

What the system is, who uses it, and how to read the rest.

One backend API, three clients, one Postgres database. Parents and teachers use a mobile app; the office and the principal use a web app; payment gateways call a webhook. Every request is scoped to one school by a claim in its token, and nothing external happens inside a database transaction.

What the product does (v1)

  • Daily student attendance, marked by the class teacher, visible to parents the same minute; absence push + SMS.
  • Staff availability: one tap by the teacher, a live 'who is in' for the principal.
  • Fees: schedules → per-student invoices → online (gateway) and offline (office) payments → gapless receipts → defaulters and reminders.
  • Teacher diary → AI-drafted, teacher-verified MCQ quiz → per-sub-topic diagnostic report for the parent, weakest sub-topics for the school.
  • Notice board, school-wide or per class, pinned and scheduled.
  • Bonafide / Transfer Certificate applications through a four-step office queue.

Roles

  • platform_admin — us. Creates and suspends schools. No school data access beyond that.
  • super_admin — the principal / owner. Everything in the school.
  • office_staff — front office. Records payments, runs the document queue, posts notices, edits students.
  • teacher — marks availability, marks attendance for the class they are class-teacher of, writes the diary and publishes quizzes for the subjects they teach.
  • guardian — a parent. Sees their children only; pays fees; applies for documents; the child's quizzes are taken from this login in the pilot.
  • student — the child's own login, reserved for later (students.user_id).

§ 2

Architecture

One API, three clients, one database; workers for everything external.

Request lifecycle

  1. request-id middleware attaches an id; every log line and audit row carries it.
  2. auth: verify JWT (HS256, 15 min), load nothing — the claims sub, school_id, role, tv are enough. Then one indexed read of users.token_version (cached 60 s in Redis) to honour logout-everywhere.
  3. tenant: the request gets a transaction-scoped SET LOCAL app.school_id so RLS policies apply as a second fence under every query.
  4. zod parses body/params/query in the route; the controller receives typed input.
  5. service runs the business rules inside one transaction; side effects are written as outbox rows.
  6. after commit, the service enqueues the jobs that consume those rows. A crashed process between commit and enqueue is covered by the queued-status sweep.
  7. response goes through a public mapper — no row is ever serialised raw.

§ 3

Tenancy, identity & authorisation

One database, every row owned by a school; the token decides, the database double-checks.

Token shape

// access JWT — 15 min, HS256, secret ≥ 32 bytes
{ "sub": "01925c…",          // users.id
  "school_id": "01925b…",    // NULL for platform_admin
  "role": "teacher",
  "tv": 3,                    // users.token_version
  "iat": …, "exp": … }

// refresh token — 30 days, opaque 32-byte random,
// stored as sha256 in refresh_tokens, rotated on use

The mobile app keeps tokens in the OS keychain. The admin web app keeps them in an httpOnly, Secure, SameSite=Lax cookie with an Origin check on unsafe methods. Nothing is ever read from localStorage.

Row-Level Security — the second fence

-- once per tenant-scoped table
ALTER TABLE attendance_records ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant ON attendance_records
  USING (school_id = current_setting('app.school_id')::uuid);

-- per request, inside the transaction
SET LOCAL app.school_id = '01925b…';

-- the app role cannot bypass it; migrations run as a different role
ALTER ROLE erp_app NOBYPASSRLS;

Queries still filter by school_id explicitly — RLS is what turns a forgotten WHERE into an empty result instead of a leak. platform_admin routes run with a separate role and no tenant setting.

§ 4

Data model

38 tables, each with its columns, constraints, indexes and the reason it is shaped that way.

Thirty-eight tables in seven modules. The map below is the whole thing; every box links to its sheet. Links to schools are omitted (every tenant table has one) and links to users are drawn faint.

Conventions that apply to every table

  • Primary keys are uuid, generated by the app as UUIDv7 (time-ordered). audit_log alone uses a bigint identity.
  • Tenancy: every table carries school_id and an RLS policy, except six: schools itself; refresh_tokens and devices (owned by a user); payment_webhook_events (the tenant is not known until the payload is read); quiz_answers and notice_targets (reached only through a parent row that has one, and RLS on the parent covers the join).
  • Time: timestamptz for instants, date for school-calendar days (attendance, due dates, holidays). 'Today' is computed in schools.timezone.
  • Money: integer paise in bigint. Column names end in _paise so a rupee value can never be confused for one.
  • Soft delete: none. Rows that stop being current get a status (left, archived, cancelled, expires_at). The only hard deletes are housekeeping of tokens, devices and processed webhooks.
  • Audit: any human action that changes money, attendance or a status writes an audit_log row in the same transaction.
  • updated_at is maintained by a trigger, not by the app.

Service-level rules

  • (student_id, due_date DESC) — parent's fee screen
  • (fee_schedule_id, status) — '₹4.18L of ₹5.8L collected for Term 2' = one SUM over this
  • CHECK (status <> 'paid' OR paid_paise = amount_paise - discount_paise)
  • CHECK (status <> 'partial' OR (paid_paise > 0 AND paid_paise < amount_paise - discount_paise))
  • CHECK (status <> 'pending' OR paid_paise = 0)
Why it is shaped this way
  • Money is integer paise in BIGINT. Never NUMERIC/float in app code: Razorpay and Cashfree take integer paise, and equality checks on paid vs due must be exact.
  • Status is a stored column with CHECK constraints tying it to the amounts, rather than a generated column. waived/cancelled are human decisions the amounts cannot express, and the checks make an inconsistent row impossible to commit.
  • Amount snapshot on the invoice (not a join to the schedule). Editing a schedule after generation must not silently change what 600 families owe; admins regenerate deliberately.

§ 6

API

74 routes: method, path, who, what goes in, what comes out.

REST over HTTPS, JSON, versioned under /v1. Parent-facing screens get one aggregate endpoint each so a screen open is one round trip on a slow phone. Admin lists are cursor-paginated.

Conventions

  • Errors: { code, message, request_id, issues? }. Codes: VALIDATION 400 · UNAUTHENTICATED 401 · FORBIDDEN 403 · NOT_FOUND 404 · CONFLICT 409 · INVALID_TRANSITION 409 · UNPROCESSABLE 422 · RATE_LIMITED 429 · INTERNAL 500.
  • Pagination: ?cursor=&limit=, limit capped per route (50 or 100). Cursor = opaque base64 of the sort key.
  • Idempotency: POSTs that create money or applications accept Idempotency-Key; the key is stored in Redis for 24 h with the first response.
  • Dates: YYYY-MM-DD for calendar days; RFC 3339 for instants. Money fields are integers named *_paise.
  • Rate limits: 600 req / 5 min per user; OTP request 3 / phone / 10 min and 20 / IP / hour; webhook route exempt but signature-gated.
  • Versioning: additive changes in place; a breaking change gets /v2 for that resource. Mobile clients cannot be force-updated.

Validation

Six rungs from the wire to the database, with the schemas that matter most.

Six rungs. A request must clear every rung; the last one is the database, which is the only rung that cannot be bypassed by a bug.

rungwhat is checkedon failure
1 · TransportBody ≤ 256 KB (1 MB on the CSV import route). JSON only. Unknown keys stripped (zod .strict() on every body).413 / 415 / 400
2 · Shape (zod, in the route)Types, ranges, formats, enum membership, array bounds. The controller receives typed data and never re-checks.400 { code:'VALIDATION', issues[] }
3 · Identity & tenantJWT verified; token_version matches; school_id and role come from the token, never the body. Every query is filtered by school_id from the token; RLS repeats the filter.401 / 403
4 · Authorisation (service)Role allowed on the route AND relationship holds: guardian ↔ student via student_guardians; teacher ↔ class via class_teacher_id or class_subjects.403 — or 404 when revealing existence would leak (a student id from another school is a 404, not a 403)
5 · Business invariants (service, in the transaction)Working day, edit window, invoice balance, state-machine transition legality, one open application per type, prerequisite quiz done.409 { code:'INVALID_TRANSITION' | 'CONFLICT' } / 422
6 · Database constraintsNOT NULL, CHECK, UNIQUE, FK, partial unique indexes. The last line: a bug above this line becomes a 500 with a request id, never bad data.500 (logged with constraint name)

Representative schemas

One per risky boundary. The quiz question schema is deliberately shared by the teacher's edit route and the LLM output validator: a model response that would not be accepted from a human is not accepted from the model either.

Constraints the database enforces (summary)

  • One attendance row per student per day · one availability row per staff per day.
  • One enrollment per student per year · one current academic year per school · one class teacher per class.
  • Invoice amounts: 0 ≤ discount ≤ amount, 0 ≤ paid ≤ amount − discount, and status must agree with them.
  • One invoice per student per schedule · one gateway payment id ever · one receipt number per school · gapless counter under row lock.
  • One published quiz per class per topic · question options 2–6 with a valid correct index · one answer per question per attempt.
  • One open document application per student per type.
  • Every FK is ON DELETE RESTRICT except children of a deleted attempt / quiz draft (CASCADE) and files references (SET NULL).

§ 11

Security, privacy & operations

The baseline, the DPDP posture, logs, alerts, backups.

Security baseline

  • Secrets parsed once by a zod schema at boot; JWT secret ≥ 32 bytes; boot fails on a bad config.
  • Passwords: argon2id. OTP: 6 digits, 5-minute TTL, 5 attempts, hashed in Redis; request and verify return the same shape whether or not the phone exists.
  • Rate limits on everything; strict on auth, keyed by IP and by identifier; 429 with Retry-After.
  • CORS allowlist from config; secure headers (CSP, nosniff, no-referrer, frame DENY, HSTS); body limit 256 KB.
  • Every body .strict(); ids coerced; no client value ever reaches a WHERE without a schema.
  • Ownership in the query; RLS underneath; a foreign school's id is a 404.
  • Logs redact by key name; errors to clients carry a code and a request id, never a stack or SQL.
  • Webhooks: HMAC verified before parsing; inbox row before processing; 200 only after the insert.
  • Files are private; clients get 15-minute signed URLs; the storage key is never exposed.
  • Dependencies pinned; npm audit in CI; no package without a reason.

Privacy (DPDP-aligned)

  • Data minimisation: no location, no contacts, no analytics SDK in the parent app. What is stored is what a school register already holds.
  • Consent recorded at guardian onboarding (users gets a consent_at column in the onboarding migration).
  • Children's quiz data is visible only to their guardians, their teachers, and the school's admins; the school-wide report is aggregated, minimum 30 answers per sub-topic.
  • Right to erasure: a student record is anonymised (name, dob, address → null; admission_no kept) rather than deleted, preserving fee and attendance history the school is legally required to keep.
  • Staging gets a PII-scrubbed copy of production, never the real one.

Observability

  • One JSON log line per request: ts level request_id school_id user_id role method path status ms. Errors add code and cause.
  • Job logs carry job_id queue attempt and the row id they act on.
  • Metrics: p50/p95 per route, queue depth and age per queue, webhook lag (received_at − gateway's created_at), failed notification rate.
  • Alerts: webhook lag > 5 min, payments 'initiated' > 30 min, queue age > 2 min, error rate > 1 %, Postgres connections > 80 %.

Backups & recovery

  • Managed Postgres with PITR, 7-day window; nightly logical dump to object storage in a second provider.
  • Restore rehearsed before the first paying school and quarterly after: dump → fresh instance → run the smoke suite → record the time it took.
  • Object storage versioning on; receipts are also reproducible from fee_payments.

Schema change rules

  • Every schema change is a numbered migration file, forward-only, applied in CI against a copy of production before deploy.
  • Additive changes (new nullable column, new table, new index CONCURRENTLY) ship freely. Renames and type changes ship as add → backfill → switch reads → drop, across separate deploys.
  • Never drop a column that a running version of the mobile app still reads; the app cannot be force-updated on a parent's phone.
  • Enum growth is `ALTER TYPE … ADD VALUE`; enum shrink is never done (mark the value deprecated in code).
  • New index on a big table: CREATE INDEX CONCURRENTLY, outside a transaction.
  • A migration that touches fee_* or attendance_records is reviewed by two people and run with a fresh backup taken first.
